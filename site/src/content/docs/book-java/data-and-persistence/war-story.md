## 当 标签 变成炸弹

*改编自真实事件。*

故事从一个看起来完全合理的决定开始。支付团队想知道每个用户的请求延迟分布，于是给延迟直方图加了一个 标签：`user_id`。代码 评审 的时候没人反对——信息越多越好，对吧？指标嘛，多一个维度而已。

第一周一切正常。第二周，值班人员收到告警：Prometheus 的内存用量翻了三倍。第三周，查询开始超时，Grafana 的面板打开要一分钟。第四周，账单来了：托管监控的费用涨了五倍，因为按时间序列数量计费。每个用户就是一条独立的时间序列，几百万用户就是几百万条序列，再乘以直方图的十几个 桶。

救火的过程很狼狈。先加内存，内存追不上序列的增长速度。然后紧急改代码去掉 标签，但已经产生的高基数序列还要在数据库里躺到 保留期 期满，继续占空间、继续被扫描。最后的账：监控费用超支，整个季度的可观测性预算烧掉一半，外加两周的 值班 噩梦。

复盘的时候大家才看清：这是建模错误，不是监控错误。指标的 标签 就是它的维度，就是它的分片键。把无界基数的字段（user_id、订单号、IP）塞进 标签，等于宣布"我的每个用户都值得一条独立的时间序列"——没有业务问题需要这个答案。

正确的做法本章早就讲过：按访问模式建模。你真正要回答的问题是"延迟分布有没有变坏"，不是"用户 884213 的 p99 是多少"。前者用聚合直方图就够了，后者是 追踪 的工作——给异常请求打标，用追踪去查，而不是用指标去存。

事后他们总结出两条嗅觉。第一，标签 的基数决定了时间序列的数量，时间序列的数量决定了账单。写指标代码的时候，没人觉得自己在花钱，但每一行 标签 都是在签支票。第二，可观测性本身也需要被观测。Prometheus 的内存告警是第一个信号，但团队花了整整一周，才把"内存涨了"和"我们加了个 标签"连起来——因为加 标签 的人和看告警的人不是同一拨。

修复也很诚实：他们没做更聪明的聚合，而是做了更少的事。user_id 的 标签 删了，换成 user_tier（免费、付费、企业三档），基数从几百万降到三。想知道单个用户的延迟？那是 追踪 的活，给请求打上 trace id 去查。指标回答群体问题，追踪 回答个体问题——这个分工被写进团队的观测规范，评审 指标代码时专门检查 标签 基数。

教训很简单：高基数是数据建模问题，不是监控调优问题。标签 就是 模式，模式 要为查询服务。写下指标之前，先问一句：这个维度，真的有人会按它查吗？答不上来，就别加。
