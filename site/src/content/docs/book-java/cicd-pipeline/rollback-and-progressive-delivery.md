## 发布应该是可逆的

再完善的测试也拦不住所有 bug。总有漏网之鱼溜到生产。所以问题不是"如何保证没 bug"，而是"bug 上线了，多快能发现、多快能止血"。

答案是让发布可逆，并且让爆炸半径可控。

## 三种姿势

1. **蓝绿部署**——准备两套一模一样的环境，蓝的跑着旧版本，绿的部署新版本。切流量过去，发现不对再切回来。回滚 = 切流量，秒级。代价是双倍资源。
2. **金丝雀发布**——先给 1% 的用户上新版本，观察指标，没问题再 10%、50%、100%。最早发现问题的永远是真实用户，但只有 1% 的用户会疼。需要配套的监控和自动熔断——指标一崩，自动切回。
3. **特性开关**——代码里埋开关，新功能默认关闭，上线后按用户、按比例、按时间逐步打开。出问题？关开关就行，不用重新部署。代价是代码里多了分支，开关的清理是长期家务。

三种可以组合：金丝雀 + 特性开关是最常见的生产姿势。

## 开关的家务

特性开关最大的坑是**烂尾开关**：功能全量了，开关还留在代码里，三年后没人敢删——"万一还有人在用呢"。规矩：每个开关建的时候就写好**过期日期**，过期自动提醒清理。开关是脚手架，不是家具。

## 反模式

**周五下午上线**：所有人都知道周五不上线，但总有"这个改动很小"的例外。然后周六凌晨三点，群里开始 @ 所有人。

这不是技术问题，是纪律问题。规定写下来：周四之后不发生产，除非 P0 修复。架构师的工作，有一半是建立这种让人少加班的纪律。
