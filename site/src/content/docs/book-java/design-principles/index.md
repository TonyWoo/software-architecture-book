设计原则不是装饰品，是生存策略。你写的每一个系统都会被改，而改它的人就是六个月后的你自己——凌晨两点，盯着一段你曾发誓只是"临时方案"的代码。

本章的所有原则都在回答同一个问题：怎么让软件保持柔软？怎么让改动便宜而不是可怕？SOLID 给你五条战术规则。边界告诉你线画在哪里。依赖倒置告诉你线应该朝哪个方向。简单原则阻止你建造空中楼阁。复杂度预算提醒你，聪明是有限资源——花在刀刃上。

这些都不是法律，是胜率很高的权衡。改动压力真实存在的地方就用它，不存在的地方就别用。好的架构师懂原则，伟大的架构师知道什么时候打破它们。

**贯穿案例 · 快存科技**

快存科技是家虚构的存储厂商，官网卖内存和固态硬盘。这一幕发生在 2017 年。

那年代码涨到 20 万行，团队 12 个人。一个看起来人畜无害的需求："选型器加一个'按容量筛选'。"开发组估了三天，第五天还在联调。改兼容逻辑的时候牵出三个缺陷：机型匹配的规则藏在三处，容量换算在另一处，"DDR4"和"DDR5"的判定散落在五个文件里。修好一个，漏掉两个。

那天下午，老板叫停所有新功能两周——做"边界清理"。第一周只干一件事：按模块分包。选型、目录、订单、库存，一包一件事，包和包之间只能通过接口说话，循环依赖直接报错。第二周做依赖倒置：选型核心不再引用数据库驱动，所有外部依赖翻成端口。SOLID 的战术只用在真正会变的地方——兼容引擎是业务的心脏，配得上讲究；静态页面和新闻资讯继续保持无聊。

代价很真实：两周零交付，老板在站会上拍了两次桌子。收获也很真实：两个月后，又一个选型需求下来——"服务器内存按主板芯片组过滤"——这次只动了一个包。改动的影响停在了线里，回归测试从三天缩到半天。

本幕的知识点：内聚耦合（一起变的东西住一起，改一个地方坏三个地方就是耦合太紧）、边界（变化到此为止的线）、复杂度预算（两周的清理预算，全砸在了兼容引擎这条差异化上）。
