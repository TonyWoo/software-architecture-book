# 第10章 持续集成与持续部署 · 本章导读

<iframe src="/software-architecture-book/figures/hairline-locks.html" width="400" height="320" loading="lazy" title="本章插画" style="border:none;max-width:100%;display:block;margin:0 auto;"></iframe>
<p style="text-align:center;"><small>💡 鼠标悬停可交互</small></p>

很多架构图画到"服务"就停了，好像代码写完、服务画出来，工作就结束了。但用户用的不是架构图，是跑起来的软件。代码从你的笔记本到用户手里，中间那条路——构建、测试、发布、部署——本身就是架构的一部分，而且是出故障最多的部分。

本章讲的就是这条路。我们会看：为什么流水线设计是架构师的事；一条健康的流水线分哪几个阶段；环境和配置如何管理才不会"在我机器上是好的"；数据库迁移这个最容易翻车的地方怎么处理；以及当发布出问题时，如何优雅地回滚或者渐进放量。

把它们串起来的主题是：**交付能力是架构质量的一部分**。一个需要三天才能上线的"优雅架构"，不如一个一小时就能安全上线的"普通架构"。

**贯穿案例 · 快存科技**

快存科技的官网从第一天就搭了流水线：代码合并自动构建、跑测试、部署到预发环境。但官网有两条流水线：一条跑代码（选型器、商城），一条跑内容（产品页、新闻、兼容数据）。老板问"为什么新产品页还没上线"，技术负责人指着内容流水线说："已经在路上了，38 分钟后到。"——这就是本章要讲的东西：代码和内容，两条流水线，同一套纪律。
