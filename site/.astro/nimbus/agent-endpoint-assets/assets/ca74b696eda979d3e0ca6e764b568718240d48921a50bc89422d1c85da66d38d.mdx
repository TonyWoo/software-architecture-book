title: "战争故事"
description: "周五下午的\"小改动\"，让全站挂了六个小时。"
---

（改编自真实事件。）

那是一个周五下午四点。

小李改了一行配置——把某个超时的默认值从 30 秒改成 5 秒。改动很小，评审的人看了一眼就过了："就改个数字，能出什么事。"代码合并，流水线启动，测试全绿。五点，部署到生产。

五点零三分，告警炸了。

那个"小数字"是个全局默认值，30 秒改成 5 秒之后，所有调用下游服务的请求，5 秒没回来就掐断。而下游有个报表服务，正常就要跑 8 秒。于是订单服务开始大面积超时，超时触发重试，重试把下游打得更慢，更慢导致更多超时——经典的重试风暴。一小时后，核心链路全挂。

复盘时发现三件事，每件都够写进本章：

第一，**配置和代码一起发布，却没有一起评审**。那行配置变更藏在代码提交里，评审人只看了 Java 代码，没注意到配置文件也动了。配置也是代码，走同样的评审（第 3 节）。

第二，**没有金丝雀**。全量发布，一次推出去。如果先给 1% 的流量，5 秒超时的锅在 1% 的用户身上就会冒出来，而不是全站（第 5 节）。

第三，**回滚花了四十分钟**。因为配置是跟着代码版本走的，回滚代码版本时，配置也被"回滚"到了一个更早但同样有问题的版本——没人分得清哪个版本的配置是对的。最后是运维手动改回去的（第 3 节：配置进版本控制，变更可追踪）。

最讽刺的是：周五下午不发版的规定，白纸黑字贴在墙上。但"这个改动很小"这句话，比任何规定都有说服力。

从那以后，团队立了两条铁律：配置变更单独走评审，流水线里加一道"配置 diff"展示；周四之后的生产发布，必须两个人同时在场，一个人点按钮，一个人盯着监控看。

小改动没有"小"的。让发布变便宜、变可逆（第 5 节），比祈祷"这次别出事"可靠得多。
