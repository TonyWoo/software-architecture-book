# 流水线分阶段

## 一条典型的流水线

代码合并到主分支，流水线启动：

1. **构建**——检出代码，还原依赖，编译打包，产出一个带版本号的制品（Docker 镜像、jar 包、zip）。关键原则：**构建一次，到处部署**。不要在测试环境构建一次、生产环境再构建一次——两次构建的产物可能不一样，你就不知道测的到底是不是上的。
2. **测试**——单元测试、集成测试、契约测试按顺序跑。快的先跑，慢的后跑，失败就停。测试是流水线的守门员，不是摆设。
3. **发布**——制品推进到制品库，打上 `v1.2.3` 这样的不可变标签。从这一刻起，这个制品就是"那个"版本，谁也改不了它。
4. **部署**——按顺序推到各个环境：开发 → 测试 → 预发 → 生产。每个环境都是一次验证，预发环境要尽量像生产。

## 每阶段的取舍

**构建要快还是要全？** 全量构建最保险，但 40 分钟的构建会逼着开发者攒代码一次提交——回到大爆炸。折中：增量构建 +  nightly 全量。

**测试拦多严？** 全绿才放行最安全，但 flaky 测试（时好时坏的）会逼疯所有人。规则：单元测试必须全绿；集成测试允许重跑一次；契约测试是红线，挂了就说明有人改了接口没打招呼。

**部署自动还是手动？** 到测试环境全自动，到生产环境手动点按钮——这是大多数团队的起点。成熟之后，生产也可以自动，但要有"一键停"和"一键回滚"。

## 反模式

**流水线博物馆**：流水线有 28 个阶段，每个都是三年前某次故障后加的，没人敢删。跑一次 2 小时，开发者提交代码后去喝咖啡、开会、吃午饭，回来发现挂在第 3 阶段。

流水线和代码一样会走样。定期问：这个阶段还在抓 bug 吗？抓到的 bug 值得它的等待时间吗？不值得就删。流水线的价值是**快速反馈**，不是**仪式感**。
